# DDD × 智能体工程定制课程大纲

> **培训对象**：河北产权交易中心业务系统建设团队（1 产品 + 3 前端 + 4-5 后端）
> **培训时长**：半天（约 4 小时，含两次休息）
> **培训目标**：建立对"DDD 融合方法论"和"智能体工程"的基本认知，让团队有意识地在项目中有选择地应用，支撑 SaaS 迁自建的高质量交付
> **日期**：2026-08-07

---

## 课程设计说明（讲师备忘，不进入正文）

**面向场景的三个判断**：

1. 这是"从 SaaS 迁移到自建"的项目，最大的风险不是技术，而是团队用 SaaS 的"功能思维"去做自建系统，把 SaaS 的设计缺陷一起搬过来
2. 团队 8-9 人、朋友是二包，既缺 DDD 方法论，又缺 AI 编程工具的系统性使用经验，两个认知空白都要补
3. 一下午的时间做不到"实操级"，目标是"建立认知 + 给出可带走的实践清单"，让他们知道"有什么、什么时候用、第一步做什么"

**两条主线如何串起来**：

- DDD 解决"做对的事"：用融合方法理解业务、划定边界、设计领域模型
- 智能体工程解决"把事做对"：用 AI 工具加速原型、固化知识、保证质量
- 交汇点在"快速原型法"：DDD 提供建模方法，智能体工程提供加速引擎，两者结合让小团队也能高质量交付

**关于"MEAF"的澄清**：
用户提到的"ThoughtWorks MEAF"这个缩写，经多方交叉验证在 ThoughtWorks 官方体系中不存在。用户记忆中"DDD + 事件风暴 + 服务蓝图 + 客户旅程"的融合体系是真实存在的，业界叫 **Modern DDD** 或 **Collaborative Modelling**，由 Event Storming 发明者 Alberto Brandolini 等人推动。课程中直接用"Modern DDD 融合方法论"这个业界通称。

## 开场：破冰 + 我们今天解决什么问题（15 min）

### 要点

1. **三句话定位场景**：你们正在从 SaaS 迁移到自建系统；团队 8-9 人；朋友找我说要做 DDD 培训，但我聊下来发现你们更需要的是"怎么把项目高质量交付"
2. **抛出核心问题**：SaaS 用了那么久，你们真的知道"客户要什么"吗？还是只知道"点哪个按钮"？
3. **今天的承诺**：不讲纯理论，给你们两条可落地的线--一条管"做对的事"（DDD 融合方法），一条管"把事做对"（智能体工程）

### 交付物

- 学员对"今天解决什么"的共识

## 第一篇：为什么你们现在最需要的不是 DDD 本身（40 min）

### 1.1 DDD 是什么、不是什么（10 min）

- **是什么**：Eric Evans 2003 年提出，以领域模型为核心的软件设计方法论，分战略设计（限界上下文、上下文映射）和战术设计（实体、值对象、聚合、Repository）
- **不是什么**：不是架构风格，不是微服务的同义词，不是"写一堆 Service"
- **本命场景**：业务复杂、需要长期演进的核心系统

### 1.2 单纯 DDD 的三个致命缺陷（15 min）

用一张表说清楚为什么 Eric Evans 的书读完还是不会用：

| 缺陷 | 表现 | 你们项目的对应风险 |
|------|------|------------------|
| 缺乏"如何开始"的方法 | 书告诉你限界上下文是什么，没告诉你怎么"发现"它 | 团队会直接拿 SaaS 的功能模块当限界上下文，错的 |
| 缺乏客户视角 | 偏开发者-领域专家对话，忽略最终用户 | 产品是 UI 转岗，容易陷入"画界面"而非"理业务" |
| 与现代架构脱节 | 2003 年成书，早于微服务 | 聚合怎么变成服务、事件怎么流转，书里没有 |

### 1.3 Modern DDD：融合方法才完整（15 min）

- **业界实际叫法**：Modern DDD / Collaborative Modelling（协作建模），由 Event Storming 发明者 Alberto Brandolini 等人推动
- **"MEAF"澄清**：ThoughtWorks 官方体系中没有这个缩写，但用户描述的融合体系是业界真实存在的实践
- **四方法补位 DDD 缺口**：

| DDD 的缺口 | 补位方法 | 一句话作用 |
|-----------|---------|-----------|
| 怎么理解客户视角的业务流程 | 客户旅程图 | 从客户视角描绘触点和痛点 |
| 怎么把客户体验与后台对齐 | 服务蓝图 | 5 层泳道揭示后台流程和跨部门交接 |
| 怎么快速发现领域事件和边界 | 事件风暴 | 用便利贴协作，以事件为锚点建模 |
| 怎么从事件推导命令和聚合 | 命令风暴 | Event Storming 的流程建模层级 |

### 交付物

- Modern DDD 融合方法全景图（一页纸）
- 学员理解"为什么单纯 DDD 不够"

## 第二篇：Modern DDD：从业务到领域模型的完整路径（50 min）

### 2.1 端到端流程总览（10 min）

用一张流程图把四方法串起来，让学员看到"从业务问题到可落地模型"的完整路径：

```
客户旅程（客户视角）
    ↓ 触点与痛点
服务蓝图（客户+组织视角）
    ↓ 后台流程与跨部门交接
事件风暴 Big Picture（领域视角）
    ↓ 领域事件时间线 + 候选限界上下文
命令风暴（流程视角）
    ↓ 命令、策略、读模型
事件风暴 Software Design（设计视角）
    ↓ 聚合边界
DDD 战术设计（代码视角）
    ↓ 实体、值对象、Repository
可落地的微服务架构
```

### 2.2 客户旅程图：从客户视角出发（10 min）

- **输入**：客户访谈、客服记录
- **输出**：触点序列 + 情绪曲线 + 痛点
- **对你们项目的价值**：产权交易的核心角色（出让方、受让方、中介、监管）各自旅程不同，先画旅程再谈功能
- **反模式**：直接拿 SaaS 的功能清单当需求

### 2.3 服务蓝图：揭示后台流程（10 min）

- **5 层泳道**：物理证据 / 客户行为 / 前台 / 后台 / 支持流程
- **三条线**：互动线 / 可见线（最核心）/ 内部互动线
- **对你们项目的价值**：产权交易的"挂牌-报名-竞价-结算"流程，可见线之下有大量审批、公告、资金监管，服务蓝图让这些后台流程显形
- **关键洞察**：服务蓝图的"后台 + 支持流程"层直接暴露候选限界上下文

### 2.4 事件风暴：以事件为锚点建模（15 min）

- **Big Picture 层级**：全员便利贴协作，橙色 = 领域事件，按时间线排列
- **三个官方层级**：Big Picture（大图）-> Process Modeling（流程建模）-> Software Design（软件设计）
- **核心产物**：领域事件时间线 + 关键事件（Pivotal Events）+ 候选限界上下文
- **对你们项目的价值**：一次 2-3 小时的事件风暴工作坊，能让全员对"产权交易到底发生什么"达成共识
- **便利贴颜色约定**（业界标准）：
  - 橙色 = 领域事件（"挂牌已发布"）
  - 黄色 = 角色/用户
  - 蓝色 = 命令
  - 紫色 = 策略
  - 粉色 = 系统
  - 绿色 = 读模型

### 2.5 命令风暴 + Software Design：走向可落地模型（5 min）

- **命令风暴** = Event Storming 的 Process Modeling 层级，从"发生了什么"推导"谁让什么发生"
- **核心语法**：`Event -> Policy -> Command -> System -> Event`
- **Software Design 层级**：粉色系统 -> 黄色聚合，聚合边界 = 微服务候选
- **关键原则**：聚合是一致性边界，不是数据库表；一个聚合对应一个微服务候选

### 交付物

- 四方法串联流程图
- 每种方法的输入输出对照表
- 产权交易场景的颜色约定速查

## 第三篇：智能体工程：让小团队也能高质量交付（45 min）

### 3.1 先认识 Vibe Coding：你们可能已经听说过的（10 min）

- **定义**：Karpathy 2025 年 2 月提出，自然语言意图驱动、AI 自动生成代码、对话迭代
- **擅长的场景**：从零搭原型、MVP、个人工具、简单 CRUD
- **已知风险**（业界数据，不吓人但要讲）：
  - AI 协作代码的"重大问题"比纯人工多 1.7 倍（CodeRabbit 2025.12）
  - 安全漏洞多 2.74 倍
  - 在成熟代码库中做增量修改，AI 反而拖慢 19%（METR 2025.7）
- **关键分界线**：不审查 = vibe coding，审查理解 = LLM 辅助编程

### 3.2 智能体工程：从"凭感觉"到"可复利"（15 min）

- **一句话定义**：把非确定性的 LLM 协作，演化为可靠的、可复利的工程体系
- **核心区别**：

| 维度 | Vibe Coding（术） | 智能体工程（道） |
|------|------------------|----------------|
| 产出 | 单次对话的代码 | 可复用的知识资产（Skill、Prompt 模板、规范） |
| Prompt | 凭感觉写 | 结构化、有版本 |
| 改进 | 出问题再改 | 持续改进引擎：发现->学习->锻造->沉淀 |
| 能做什么 | 能做 Demo | 能持续进化 |

- **四层结构**（简化版，不讲 AFE 全称）：
  - L1 业务层：你们交付的业务系统
  - L2 Agent 团队层：Prompt、协作流程、工作规范
  - L3 工具平台层：Copilot/Cursor、MCP 等
  - L4 治理层：质量门禁、复盘机制
- **核心洞察**：问题总在 L1 暴露，根因总在上层

### 3.3 工具链：小团队怎么起步（10 min）

- **后端（Java）**：GitHub Copilot / 通义灵码 / Cursor 三选一，建议先用免费档
- **前端（Vue）**：同上，Copilot 对 Vue 支持较好
- **协作层**：把团队的 Prompt 经验、踩坑记录沉淀成共享文档（哪怕只是个 Markdown）
- **不要一上来就**：搞 MCP Server、搞 Agent 编排、搞复杂工具链

### 3.4 可带走的实践清单（10 min）

给团队一份"第一周、第一个月、第一季度"的渐进式清单：

| 阶段 | 动作 | 验收标志 |
|------|------|---------|
| 第一周 | 每人装好一个 AI 编程工具，写一个简单 CRUD | 工具能跑通 |
| 第二周 | 用 AI 工具辅助写单元测试，覆盖率到 40% | 测试能跑 |
| 第一个月 | 团队共建一份 Prompt 经验文档 | 文档有 10 条以上经验 |
| 第二个月 | 引入事件风暴工作坊，对核心流程做一次 Big Picture | 产出事件时间线 |
| 第三个月 | 用 DDD 战术设计重构一个核心模块 | 至少一个聚合落地 |

### 交付物

- Vibe Coding vs 智能体工程对照表
- 渐进式实践清单
- 工具链起步建议

## 第四篇：两线合一：快速原型法驱动项目交付（30 min）

### 4.1 快速原型法 = DDD 建模 + 智能体加速（10 min）

- **核心思路**：DDD 提供"做对的事"的方法，智能体工程提供"把事做对"的引擎
- **一个完整的迭代循环**：
  1. 事件风暴工作坊（2-3h）-> 领域事件时间线
  2. 识别限界上下文和聚合（1h）-> 候选微服务边界
  3. 用 AI 工具快速生成原型代码（半天）-> 可运行 MVP
  4. 客户验证 -> 反馈 -> 调整模型
  5. 沉淀 Prompt 和经验到团队知识库

### 4.2 针对"产权交易中心"的落地建议（15 min）

- **第一步（本周）**：做一次"产权交易全流程"的事件风暴 Big Picture，邀请业务方参加
- **第二步（两周内）**：从事件时间线识别 3-5 个限界上下文（候选：挂牌、报名、竞价、结算、公告）
- **第三步（一个月内）**：选一个核心上下文（建议从"挂牌"开始，相对独立），用 DDD 战术设计 + AI 工具做出可运行原型
- **第四步（持续）**：每个迭代用事件风暴回顾一次，模型持续演进
- **特别提醒**：不要试图一次性设计全部微服务，按业务优先级逐个突破

### 4.3 反模式警示（5 min）

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 功能思维迁移 | 直接照搬 SaaS 的功能模块设计 | 把 SaaS 的设计缺陷一起搬过来 |
| 过度建模 | 一上来就画全量领域模型 | 分析瘫痪，迟迟不能产出代码 |
| Vibe Coding 滥用 | 不审查 AI 生成的代码 | 技术债累积，后期无法维护 |
| 工具崇拜 | 一上来搞复杂 Agent 工具链 | 投入产出比低，团队抵触 |
| 单打独斗 | Prompt 经验不共享 | 团队能力不均，关键人依赖 |

### 交付物

- 快速原型法迭代循环图
- 产权交易中心落地四步建议
- 反模式清单
