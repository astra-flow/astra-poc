# DDD × 智能体工程定制课程讲稿（上半部分）

> **说明**：本讲稿为讲师口语化讲授脚本，包含讲授要点、过渡话术、互动设计。
> 标注【板书】的内容建议写在白板/PPT上；【互动】为与学员的交互环节。
> 总时长约 210 分钟（3.5 小时），留 30 分钟弹性。

## 开场：破冰 + 我们今天解决什么问题（15 min）

### 讲师话术

"大家好，感谢大家今天下午的时间。我先做个自我介绍——我是苏威，目前在集团研发总院负责研发效能和 AI 平台相关的工作。"

"你们老板找我聊的时候，说的是'给我们团队做个 DDD 培训'。但我跟他聊完之后，发现你们现在最需要的可能不是 DDD 本身。"

"为什么这么说？你们正在做一个什么事？从 SaaS 迁移到自建系统。团队 8-9 个人，时间紧任务重。这种情况下，如果我跟你们讲三个小时的 Eric Evans 原著理论，你们回去还是不知道怎么用。"

"所以今天下午，我给你们两条线——一条管'做对的事'，一条管'把事做对'。两条线合在一起，就是你们现在最需要的：快速原型法驱动项目高质量交付。"

【互动】"先问大家一个问题：你们用那个 SaaS 平台多久了？"

（等回答）

"好，那第二个问题：用了这么久，你们真的知道'客户要什么'吗？还是只知道'点哪个按钮'？"

（停顿，让问题落地）

"这个问题不急着回答。今天下午结束的时候，我希望你们能带着答案走。"

### 今天的承诺

"不讲纯理论。给你们两条可落地的线："

1. "做对的事"——用 DDD 融合方法理解业务、划定边界
2. "把事做对"——用 AI 工具加速原型、保证质量

"好，我们开始。"

## 第一篇：为什么你们现在最需要的不是 DDD 本身（40 min）

### 1.1 DDD 是什么、不是什么（10 min）

"先花 10 分钟对齐一下 DDD 的基本概念。知道的就当复习，不知道的正好补上。"

"DDD 全称 Domain-Driven Design，领域驱动设计。Eric Evans 2003 年出的书，到现在 20 多年了。"

"它分两大部分："

- "战略设计：限界上下文、上下文映射——解决'怎么划边界'的问题"
- "战术设计：实体、值对象、聚合、Repository——解决'怎么写代码'的问题"

【板书】画一个简单的分层图：

```
战略设计（划边界）→ 限界上下文、上下文映射
战术设计（写代码）→ 实体、值对象、聚合、Repository
```

"但我要强调 DDD 不是什么："

- "不是架构风格——它不是微服务的同义词"
- "不是'写一堆 Service'——很多人学了 DDD 之后，代码里全是 Service，实体反而成了空壳"
- "不是银弹——它最适合业务复杂、需要长期演进的核心系统"

"你们这个产权交易系统，恰恰就是 DDD 的本命场景——业务复杂、规则多、需要长期维护。"

### 1.2 单纯 DDD 的三个致命缺陷（15 min）

"但是，如果你们现在回去读 Eric Evans 的原著，读完大概率还是不会用。为什么？三个致命缺陷。"

【板书】画一张表：

| 缺陷 | 表现 | 你们项目的对应风险 |
|------|------|------------------|
| 缺乏"如何开始"的方法 | 书告诉你限界上下文是什么，没告诉你怎么"发现"它 | 团队会直接拿 SaaS 的功能模块当限界上下文，错的 |
| 缺乏客户视角 | 偏开发者-领域专家对话，忽略最终用户 | 产品是 UI 转岗，容易陷入"画界面"而非"理业务" |
| 与现代架构脱节 | 2003 年成书，早于微服务 | 聚合怎么变成服务、事件怎么流转，书里没有 |

"第一个缺陷最致命。你们现在最大的风险是什么？是团队用 SaaS 的'功能思维'去做自建系统。"

【互动】"我问你们，SaaS 上的'挂牌管理'这个模块，你们觉得它是一个限界上下文吗？"

（等回答）

"答案是：不一定。SaaS 的功能模块是按'操作便利性'划分的，不是按'业务语义边界'划分的。如果你们直接拿 SaaS 的功能模块当限界上下文，等于把 SaaS 的设计缺陷一起搬过来。"

"第二个缺陷：缺乏客户视角。你们的产品经理是 UI 转岗的对吧？这不是贬义，但 UI 出身的 PM 容易陷入'画界面'的思维——先想页面长什么样，再想业务怎么走。DDD 的融合方法要求你先想'客户经历了什么'，再想'系统要做什么'。"

"第三个缺陷：与现代架构脱节。2003 年还没有微服务，还没有事件驱动架构。书里告诉你聚合是什么，但没告诉你聚合怎么变成微服务。这个缺口需要后来的方法补上。"

### 1.3 Modern DDD：融合方法才完整（15 min）

"所以业界后来发展出了一套融合方法，把 DDD 的缺口补上了。这套方法有几个名字：Modern DDD、Collaborative Modelling（协作建模）。"

"顺便说一句，你们老板提到的'MEAF'——我专门查过，ThoughtWorks 官方体系中没有这个缩写。但你们老板描述的那个'DDD + 事件风暴 + 服务蓝图 + 客户旅程'的融合体系，是真实存在的。推动它的人是 Event Storming 的发明者 Alberto Brandolini。"

"这套融合方法用四个方法补了 DDD 的四个缺口："

【板书】画四方法补位表：

| DDD 的缺口 | 补位方法 | 一句话作用 |
|-----------|---------|-----------|
| 怎么理解客户视角的业务流程 | 客户旅程图 | 从客户视角描绘触点和痛点 |
| 怎么把客户体验与后台对齐 | 服务蓝图 | 5 层泳道揭示后台流程和跨部门交接 |
| 怎么快速发现领域事件和边界 | 事件风暴 | 用便利贴协作，以事件为锚点建模 |
| 怎么从事件推导命令和聚合 | 命令风暴 | Event Storming 的流程建模层级 |

"这四个方法不是独立的，它们是一条完整的链路。从'客户视角'到'可落地的代码'，每一步都有明确的输入输出。"

"接下来第二篇，我们就走一遍这条完整的链路。"

【过渡话术】"休息 5 分钟，回来我们走完整路径。"

## 第二篇：Modern DDD：从业务到领域模型的完整路径（50 min）

### 2.1 端到端流程总览（10 min）

"好，我们回来。先给大家看一张完整的流程图，让你们知道今天要走的这条路长什么样。"

【板书/PPT】画流程图：

```
客户旅程（客户视角）
    ↓ 触点与痛点
服务蓝图（客户+组织视角）
    ↓ 后台流程与跨部门交接
事件风暴 Big Picture（领域视角）
    ↓ 领域事件时间线 + 候选限界上下文
命令风暴（流程视角）
    ↓ 命令、策略、读模型
事件风暴 Software Design（设计视角）
    ↓ 聚合边界
DDD 战术设计（代码视角）
    ↓ 实体、值对象、Repository
可落地的微服务架构
```

"从最上面的'客户旅程'到最下面的'可落地的微服务架构'，一共七步。每一步解决一个问题，每一步的产出是下一步的输入。"

"今天下午我们不可能走完七步，但我会让你们知道每一步是干什么的、什么时候用、怎么用。"

### 2.2 客户旅程图：从客户视角出发（10 min）

"第一步：客户旅程图。"

"什么是客户旅程图？就是从客户视角，画出他跟你系统打交道的全过程。"

"举个例子。产权交易系统有哪些角色？"

- "出让方——卖东西的"
- "受让方——买东西的"
- "中介——撮合交易的"
- "监管——看着的"

"每个角色的旅程都不一样。出让方的旅程可能是：准备材料 -> 提交挂牌 -> 等待审核 -> 查看报名 -> 确认成交。受让方的旅程可能是：浏览公告 -> 报名 -> 缴纳保证金 -> 参与竞价 -> 付款 -> 过户。"

"客户旅程图的产出是什么？三个东西：触点序列、情绪曲线、痛点标注。"

【互动】"你们觉得，在产权交易这个场景里，客户最大的痛点是什么？"

（等回答）

"对，信息不透明。出让方不知道有多少人报名，受让方不知道对手出价多少。这些痛点，就是你们系统要解决的核心问题。"

"反模式：不要直接拿 SaaS 的功能清单当需求。SaaS 的功能是按'能做什么'划分的，客户旅程是按'客户经历了什么'划分的。这是两种完全不同的视角。"

### 2.3 服务蓝图：揭示后台流程（10 min）

"第二步：服务蓝图。"

"客户旅程只画了客户能看到的部分。但一个产权交易系统，客户看不到的部分比看得到的多得多。"

"服务蓝图有 5 层泳道："

1. "物理证据——合同、公告、收据"
2. "客户行为——客户做了什么"
3. "前台——客服、窗口"
4. "后台——审批、审核、结算"
5. "支持流程——资金监管、系统运维"

"还有三条线："

- "互动线——客户和前台的分界"
- "可见线——前台和后台的分界（最核心）"
- "内部互动线——后台和支持流程的分界"

【板书】画一个简单的服务蓝图框架：

```
物理证据 |  公告   |  收据   |  合同
客户行为 | 浏览公告 | 报名   | 缴费
──────── 互动线 ────────
前台     | 咨询    | 受理   | 通知
──────── 可见线 ────────
后台     | 审核    | 对账   | 结算
──────── 内部互动线 ─────
支持流程 | 资金监管 | 系统维护
```

"对你们项目的价值在哪里？产权交易的'挂牌-报名-竞价-结算'流程，可见线之下有大量审批、公告、资金监管。服务蓝图让这些后台流程显形。"

"关键洞察：服务蓝图的'后台 + 支持流程'层，直接暴露候选限界上下文。比如'审核'是一个候选上下文，'资金监管'是另一个。"

### 2.4 事件风暴：以事件为锚点建模（15 min）

"第三步：事件风暴。这是今天下午最核心的一个方法。"

"事件风暴是谁发明的？Alberto Brandolini，2013 年。他当时发现，传统的需求分析方法——写文档、画用例图——效率太低。他发明了一种用便利贴协作的方法，让业务人员和开发人员一起，在墙上贴出整个业务流程。"

"事件风暴有三个层级："

1. "Big Picture（大图）——探索整个业务领域"
2. "Process Modeling（流程建模）——聚焦单一流程"
3. "Software Design（软件设计）——聚焦单一限界上下文"

"今天我们重点讲 Big Picture。"

"Big Picture 怎么做？很简单："

- "所有人站在一面墙前"
- "用橙色便利贴写'领域事件'——就是业务中发生的事情"
- "按时间线排列"
- "然后添加角色、命令、策略、系统"

"便利贴颜色约定（业界标准）："

【板书】画颜色约定：

```
橙色 = 领域事件（"挂牌已发布""报名已提交"）
黄色 = 角色/用户
蓝色 = 命令（"发布挂牌""提交报名"）
紫色 = 策略（"如果保证金不足，报名失败"）
粉色 = 系统
绿色 = 读模型（"查看挂牌详情"）
```

"一次 2-3 小时的事件风暴工作坊，能让全员对'产权交易到底发生什么'达成共识。这是你们下周就可以做的事。"

【互动】"我们来试一个。产权交易的第一步是什么？"

（等回答）

"对，'出让方提交挂牌申请'。这是一个命令（蓝色）。那它触发了什么事件？"

（等回答）

"'挂牌申请已提交'（橙色）。然后呢？"

（等回答）

"'审核通过'或'审核驳回'。好，你们看，就这么简单，几分钟就理清了第一步。"

### 2.5 命令风暴 + Software Design：走向可落地模型（5 min）

"第四、五步：命令风暴和 Software Design。"

"命令风暴就是 Event Storming 的 Process Modeling 层级。从'发生了什么'推导'谁让什么发生'。"

"核心语法："

【板书】`Event -> Policy -> Command -> System -> Event`

"举个例子："

- "事件：'挂牌申请已提交'"
- "策略：'如果金额超过 100 万，需要人工审核'"
- "命令：'审核挂牌申请'"
- "系统：'审核系统'"
- "事件：'挂牌审核通过'"

"Software Design 层级：粉色系统 -> 黄色聚合。聚合边界 = 微服务候选。"

"关键原则：聚合是一致性边界，不是数据库表。一个聚合对应一个微服务候选。"

"比如'挂牌'是一个聚合，'报名'是另一个聚合。它们各自是一个微服务候选。"

"好，上半场到这里。休息 10 分钟，回来我们讲智能体工程。"

【过渡话术】"刚才我们讲了'做对的事'的方法论。下半场我们讲'把事做对'——怎么用 AI 工具加速这一切。"
