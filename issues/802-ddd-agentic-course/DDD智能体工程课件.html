DDD × 智能体工程
高质量交付的方法与引擎

一条管"做对的事"（DDD 融合方法），一条管"把事做对"（智能体工程）——两线合一，让小团队也能高质量交付。
培训对象：河北产权交易中心业务系统建设团队
团队规模：1 产品 + 3 前端 + 4-5 后端
时长：约 4 小时（含两次休息）
日期：2026-08-07
课程目标

今天我们一起来解决什么

这是一个"从 SaaS 迁自建"的项目，最大的风险不是技术，而是用 SaaS 的"功能思维"去做自建系统。

认知目标

建立对"DDD 融合方法论"和"智能体工程"的基本认知，知道有什么、什么时候用。

应用目标

让团队有意识地在项目中有选择地应用，支撑 SaaS 迁自建的高质量交付。

带走目标

拿到一份可落地的实践清单与第一周行动项，知道"第一步做什么"。

一下午做不到"实操级"，目标是 建立认知 + 给出可带走的清单。

开场 · 15 min

破冰：我们今天解决什么问题

  • 三句话定位场景：你们正在从 SaaS 迁移到自建系统；团队 8-9 人；朋友说要做 DDD 培训，但聊下来发现你们更需要的是"怎么把项目高质量交付"。
  • 抛出核心问题：SaaS 用了那么久，你们真的知道"客户要什么"吗？还是只知道"点哪个按钮"？
  • 今天的承诺：不讲纯理论，给你们两条可落地的线——一条管"做对的事"（DDD 融合方法），一条管"把事做对"（智能体工程）。
交付物：学员对"今天解决什么"的共识。
01
第一篇 · 40 min

为什么你们现在最需要的不是 DDD 本身

1.1 · 10 min

DDD 是什么、不是什么

是什么

Eric Evans 2003 年提出，以领域模型为核心的软件设计方法论。分战略设计（限界上下文、上下文映射）和战术设计（实体、值对象、聚合、Repository）。

不是什么

不是架构风格，不是微服务的同义词，不是"写一堆 Service"。

本命场景：业务复杂、需要长期演进的核心系统。
1.2 · 15 min

单纯 DDD 的三个致命缺陷

为什么 Eric Evans 的书读完还是不会用？

缺陷表现你们项目的对应风险
缺乏"如何开始"的方法书告诉你限界上下文是什么，没告诉你怎么"发现"它团队会直接拿 SaaS 的功能模块当限界上下文，错的
缺乏客户视角偏开发者-领域专家对话，忽略最终用户产品是 UI 转岗，容易陷入"画界面"而非"理业务"
与现代架构脱节2003 年成书，早于微服务聚合怎么变成服务、事件怎么流转，书里没有
1.3 · 15 min

Modern DDD：融合方法才完整

业界通称 Modern DDD / Collaborative Modelling（协作建模），由 Event Storming 发明者 Alberto Brandolini 等人推动。

DDD 的缺口补位方法一句话作用
怎么理解客户视角的业务流程客户旅程图从客户视角描绘触点和痛点
怎么把客户体验与后台对齐服务蓝图5 层泳道揭示后台流程和跨部门交接
怎么快速发现领域事件和边界事件风暴用便利贴协作，以事件为锚点建模
怎么从事件推导命令和聚合命令风暴Event Storming 的流程建模层级
交付物：Modern DDD 融合方法全景图（一页纸）；学员理解"为什么单纯 DDD 不够"。
02
第二篇 · 50 min

Modern DDD：从业务到领域模型的完整路径

2.1 · 10 min

端到端流程总览

从业务问题到可落地模型的完整路径：

客户旅程客户视角
↓ 触点与痛点
服务蓝图客户 + 组织视角
↓ 后台流程与跨部门交接
事件风暴 Big Picture领域视角
↓ 领域事件时间线 + 候选限界上下文
命令风暴流程视角
↓ 命令、策略、读模型
事件风暴 Software Design设计视角
↓ 聚合边界
DDD 战术设计代码视角
↓ 实体、值对象、Repository
可落地的微服务架构
2.2 · 10 min

客户旅程图：从客户视角出发

  • 输入：客户访谈、客服记录
  • 输出：触点序列 + 情绪曲线 + 痛点
  • 对你们的价值：出让方、受让方、中介、监管各自旅程不同，先画旅程再谈功能
  • 反模式：直接拿 SaaS 的功能清单当需求
2.3 · 10 min

服务蓝图：揭示后台流程

  • 5 层泳道：物理证据 / 客户行为 / 前台 / 后台 / 支持流程
  • 三条线：互动线 / 可见线（最核心） / 内部互动线
  • 对你们的价值：产权的"挂牌-报名-竞价-结算"流程，可见线之下有大量审批、公告、资金监管，服务蓝图让后台流程显形
  • 关键洞察：服务蓝图的"后台 + 支持流程"层直接暴露候选限界上下文
2.4 · 15 min

事件风暴：以事件为锚点建模

  • Big Picture 层级：全员便利贴协作，橙色 = 领域事件，按时间线排列
  • 三个官方层级：Big Picture → Process Modeling → Software Design
  • 核心产物：领域事件时间线 + 关键事件（Pivotal Events）+ 候选限界上下文
  • 对你们的价值：一次 2-3 小时工作坊，让全员对"产权交易到底发生什么"达成共识

便利贴颜色约定（业界标准）

橙色 = 领域事件
黄色 = 角色/用户
蓝色 = 命令
紫色 = 策略
粉色 = 系统
绿色 = 读模型
2.5 · 5 min

命令风暴 + Software Design：走向可落地模型

  • 命令风暴 = Event Storming 的 Process Modeling 层级，从"发生了什么"推导"谁让什么发生"
  • 核心语法：Event → Policy → Command → System → Event
  • Software Design 层级：粉色系统 → 黄色聚合，聚合边界 = 微服务候选
  • 关键原则：聚合是一致性边界，不是数据库表；一个聚合对应一个微服务候选
交付物：四方法串联流程图 · 每种方法的输入输出对照表 · 产权交易场景颜色约定速查。

第三篇 · 45 min

智能体工程：让小团队也能高质量交付

3.1 · 10 min

先认识 Vibe Coding

  • 定义：Karpathy 2025 年 2 月提出，自然语言意图驱动、AI 自动生成代码、对话迭代
  • 擅长：从零搭原型、MVP、个人工具、简单 CRUD
  • 关键分界线：不审查 = vibe coding；审查理解 = LLM 辅助编程
1.7×
AI 协作代码的"重大问题"比纯人工多（CodeRabbit 2025.12）
2.74×
安全漏洞更多
−19%
成熟代码库增量修改，AI 反而拖慢（METR 2025.7）
3.2 · 15 min

智能体工程：从"凭感觉"到"可复利"

一句话定义：把非确定性的 LLM 协作，演化为可靠的、可复利的工程体系。

维度Vibe Coding（术）智能体工程（道）
产出单次对话的代码可复用的知识资产（Skill、Prompt 模板、规范）
Prompt凭感觉写结构化、有版本
改进出问题再改持续改进引擎：发现→学习→锻造→沉淀
能做什么能做 Demo能持续进化
3.2 · 15 min

智能体工程的四层结构

L1 业务层你们交付的业务系统
↑ 问题在此暴露
L2 Agent 团队层Prompt、协作流程、工作规范
↑ 根因在此
L3 工具平台层Copilot / Cursor、MCP 等
↑
L4 治理层质量门禁、复盘机制
核心洞察：问题总在 L1 暴露，根因总在上层。
3.3 · 10 min

工具链：小团队怎么起步

  • 后端（Java）：GitHub Copilot / 通义灵码 / Cursor 三选一，建议先用免费档
  • 前端（Vue）：同上，Copilot 对 Vue 支持较好
  • 协作层：把团队的 Prompt 经验、踩坑记录沉淀成共享文档（哪怕只是个 Markdown）
  • 不要一上来就：搞 MCP Server、搞 Agent 编排、搞复杂工具链
3.4 · 10 min

可带走的实践清单

阶段动作验收标志
第一周每人装好一个 AI 编程工具，写一个简单 CRUD工具能跑通
第二周用 AI 工具辅助写单元测试，覆盖率到 40%测试能跑
第一个月团队共建一份 Prompt 经验文档文档有 10 条以上经验
第二个月引入事件风暴工作坊，对核心流程做一次 Big Picture产出事件时间线
第三个月用 DDD 战术设计重构一个核心模块至少一个聚合落地
交付物：Vibe Coding vs 智能体工程对照表 · 渐进式实践清单 · 工具链起步建议。
04
第四篇 · 30 min

两线合一：快速原型法驱动项目交付

4.1 · 10 min

快速原型法 = DDD 建模 + 智能体加速

一个完整的迭代循环：

① 事件风暴工作坊（2-3h）

→ 领域事件时间线

② 识别限界上下文和聚合（1h）

→ 候选微服务边界

③ AI 工具快速生成原型（半天）

→ 可运行 MVP

④ 客户验证 → 反馈 → 调整

→ 模型持续演进

⑤ 沉淀 Prompt 和经验到团队知识库——让每一步都"可复利"。
4.2 · 15 min

针对"产权交易中心"的落地建议

  • 第一步（本周）：做一次"产权交易全流程"事件风暴 Big Picture，邀请业务方参加
  • 第二步（两周内）：从事件时间线识别 3-5 个限界上下文（候选：挂牌、报名、竞价、结算、公告）
  • 第三步（一个月内）：选一个核心上下文（建议从"挂牌"开始，相对独立），用 DDD 战术设计 + AI 工具做出可运行原型
  • 第四步（持续）：每个迭代用事件风暴回顾一次，模型持续演进
特别提醒：不要试图一次性设计全部微服务，按业务优先级逐个突破。
4.3 · 5 min

反模式警示

反模式表现后果
功能思维迁移直接照搬 SaaS 的功能模块设计把 SaaS 的设计缺陷一起搬过来
过度建模一上来就画全量领域模型分析瘫痪，迟迟不能产出代码
Vibe Coding 滥用不审查 AI 生成的代码技术债累积，后期无法维护
工具崇拜一上来搞复杂 Agent 工具链投入产出比低，团队抵触
单打独斗Prompt 经验不共享团队能力不均，关键人依赖
交付物：快速原型法迭代循环图 · 产权交易中心落地四步建议 · 反模式清单。
