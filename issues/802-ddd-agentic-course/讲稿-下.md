## 第三篇：智能体工程：让小团队也能高质量交付（45 min）

### 3.1 先认识 Vibe Coding：你们可能已经听说过的（10 min）

"好，我们回来。下半场我们讲'把事做对'——怎么用 AI 工具加速开发。"

"先问大家一个问题：你们中间谁用过 AI 编程工具？比如 GitHub Copilot、通义灵码、Cursor？"

【互动】举手调查

（等回答）

"好，大概 X 个人用过。那你们听说过'Vibe Coding'这个词吗？"

"Vibe Coding 是 Andrej Karpathy 在 2025 年 2 月提出的概念。Karpathy 是谁？OpenAI 的创始成员之一，特斯拉前 AI 总监。他说：有一种新的编程方式，叫 Vibe Coding——你完全跟着感觉走，让 AI 写代码，你甚至不读 diff，直接'Accept All'。"

"听起来很爽对吧？但我要给你们泼一盆冷水。"

"Vibe Coding 擅长的场景：从零搭原型、MVP、个人工具、简单 CRUD。说白了，就是'周末项目'。"

"但它有已知风险，而且这些风险有数据支撑："

【板书】风险数据：

| 风险维度 | 数据 | 来源 |
|---------|------|------|
| 代码质量 | AI 协作代码的"重大问题"比纯人工多 1.7 倍 | CodeRabbit 2025.12 |
| 安全漏洞 | AI 协作代码的安全漏洞多 2.74 倍 | CodeRabbit 2025.12 |
| 可维护性 | 重构比例从 25% 降至不到 10%，代码重复增加约 4 倍 | GitClear 纵向研究 |
| 调试效率 | 在成熟代码库中，AI 反而拖慢 19% | METR 2025.7 |

"这些数据不是吓你们，是让你们知道：AI 编程工具是把双刃剑。用好了是加速器，用不好是技术债加速器。"

"关键分界线是什么？Simon Willison 说得好：如果 LLM 写了每一行代码，但你审查、测试、理解了它，那不是 Vibe Coding——那是把 LLM 当打字助手。"

"不审查 = Vibe Coding，审查理解 = LLM 辅助编程。你们要选后者。"

### 3.2 智能体工程：从"凭感觉"到"可复利"（15 min）

"那什么是智能体工程？一句话定义：把非确定性的 LLM 协作，演化为可靠的、可复利的工程体系。"

"Vibe Coding 和智能体工程的区别，就像'周末钓鱼'和'经营渔场'的区别："

【板书】对照表：

| 维度 | Vibe Coding（术） | 智能体工程（道） |
|------|------------------|----------------|
| 产出 | 单次对话的代码 | 可复用的知识资产（Skill、Prompt 模板、规范） |
| Prompt | 凭感觉写 | 结构化、有版本 |
| 改进 | 出问题再改 | 持续改进引擎：发现->学习->锻造->沉淀 |
| 能做什么 | 能做 Demo | 能持续进化 |

"我给你们画一个四层结构，帮你们理解智能体工程的全貌："

【板书】画四层结构：

```
L4 治理层    质量门禁、复盘机制
L2 Agent团队层  Prompt、协作流程、工作规范
L3 工具平台层  Copilot/Cursor、MCP 等
L1 业务层    你们交付的业务系统
```

"这个结构有个核心洞察：问题总在 L1 暴露，但根因总在上层。"

"举个例子：你们用 AI 生成的代码质量不好（L1 的问题），根因可能是 Prompt 写得不够好（L2），也可能是工具配置不对（L3），也可能是没有代码审查机制（L4）。"

"所以解决问题的思路是：不要只在 L1 修修补补，要往上找根因。"

### 3.3 工具链：小团队怎么起步（10 min）

"好，说点实际的。你们 8-9 个人的团队，怎么起步？"

"后端（Java）：GitHub Copilot / 通义灵码 / Cursor 三选一。建议先用免费档试试。Copilot 对 Java 支持不错，通义灵码免费且中文支持好，Cursor 功能最强但要付费。"

"前端（Vue）：同上。Copilot 对 Vue 支持较好。"

"协作层：把团队的 Prompt 经验、踩坑记录沉淀成共享文档。哪怕只是个 Markdown 文件，也比没有强。"

"不要一上来就搞 MCP Server、搞 Agent 编排、搞复杂工具链。你们现在最需要的是：让每个人先用起来，积累经验。"

【互动】"你们团队现在有共享的技术文档吗？"

（等回答）

"好，那今天回去第一件事：建一个共享文档，叫'AI 编程踩坑记录'。谁遇到什么问题、怎么解决的，写进去。"

### 3.4 可带走的实践清单（10 min）

"最后，给你们一份渐进式实践清单。不要想一口吃成胖子，按节奏来："

【板书】实践清单：

| 阶段 | 动作 | 验收标志 |
|------|------|---------|
| 第一周 | 每人装好一个 AI 编程工具，写一个简单 CRUD | 工具能跑通 |
| 第二周 | 用 AI 工具辅助写单元测试，覆盖率到 40% | 测试能跑 |
| 第一个月 | 团队共建一份 Prompt 经验文档 | 文档有 10 条以上经验 |
| 第二个月 | 引入事件风暴工作坊，对核心流程做一次 Big Picture | 产出事件时间线 |
| 第三个月 | 用 DDD 战术设计重构一个核心模块 | 至少一个聚合落地 |

"注意节奏：第一周只是'装工具写个 CRUD'，门槛很低。第二周开始写测试。第一个月才建文档。第二个月才引入事件风暴。"

"为什么这么慢？因为习惯需要时间培养。你们现在最怕的是什么？是'学了一堆方法论，回去一个都没用'。"

"所以我的建议是：先让 AI 工具成为日常习惯，再逐步引入方法论。"

【过渡话术】"好，最后 30 分钟，我们把两条线合在一起。"

## 第四篇：两线合一：快速原型法驱动项目交付（30 min）

### 4.1 快速原型法 = DDD 建模 + 智能体加速（10 min）

"今天下午我们讲了两条线："
- "DDD 融合方法——做对的事"
- "智能体工程——把事做对"

"现在把它们合在一起：快速原型法。"

"核心思路很简单：DDD 提供'做什么'的方法，智能体工程提供'怎么做'的引擎。"

"一个完整的迭代循环："

【板书】迭代循环：

```
1. 事件风暴工作坊（2-3h）-> 领域事件时间线
2. 识别限界上下文和聚合（1h）-> 候选微服务边界
3. 用 AI 工具快速生成原型代码（半天）-> 可运行 MVP
4. 客户验证 -> 反馈 -> 调整模型
5. 沉淀 Prompt 和经验到团队知识库
```

"这个循环的关键是什么？快。"

"传统做法：需求分析 2 周 -> 设计 1 周 -> 开发 4 周 -> 测试 2 周 -> 上线。等客户看到东西，已经两个月过去了。"

"快速原型法：事件风暴 2-3 小时 -> 识别边界 1 小时 -> AI 生成原型半天。第二天客户就能看到可运行的东西。"

"客户看到原型之后，反馈是具体的、可操作的。而不是'这个需求文档我看不懂'。"

### 4.2 针对"产权交易中心"的落地建议（15 min）

"好，针对你们的具体情况，我给你们四步建议："

【板书】四步建议：

"第一步（本周）：做一次'产权交易全流程'的事件风暴 Big Picture，邀请业务方参加。"

"怎么做？找一面大墙，买几包便利贴（橙色、黄色、蓝色、紫色、粉色、绿色），把业务方和开发团队叫到一起。2-3 小时，把产权交易的全流程贴出来。"

"产出物：一张照片 + 事件清单。就这么简单。"

"第二步（两周内）：从事件时间线识别 3-5 个限界上下文。"

"候选：挂牌、报名、竞价、结算、公告。每个上下文是一个独立的业务能力域。"

"第三步（一个月内）：选一个核心上下文，用 DDD 战术设计 + AI 工具做出可运行原型。"

"建议从'挂牌'开始。为什么？因为挂牌相对独立，不依赖其他上下文。而且挂牌是产权交易的起点，做出来就能看到价值。"

"第四步（持续）：每个迭代用事件风暴回顾一次，模型持续演进。"

"特别提醒：不要试图一次性设计全部微服务。按业务优先级逐个突破。先做挂牌，再做报名，再做竞价……"

### 4.3 反模式警示（5 min）

"最后，给你们五个反模式，你们一定要注意："

【板书】反模式清单：

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 功能思维迁移 | 直接照搬 SaaS 的功能模块设计 | 把 SaaS 的设计缺陷一起搬过来 |
| 过度建模 | 一上来就画全量领域模型 | 分析瘫痪，迟迟不能产出代码 |
| Vibe Coding 滥用 | 不审查 AI 生成的代码 | 技术债累积，后期无法维护 |
| 工具崇拜 | 一上来搞复杂 Agent 工具链 | 投入产出比低，团队抵触 |
| 单打独斗 | Prompt 经验不共享 | 团队能力不均，关键人依赖 |

"第一个反模式是你们最大的风险。你们用了那么久的 SaaS，很容易不自觉地按照 SaaS 的功能模块来设计系统。但 SaaS 的功能是按'操作便利性'划分的，不是按'业务语义边界'划分的。"

"第二个反模式：过度建模。不要试图一开始就把所有领域模型画完。先做核心流程，再逐步细化。"

"第三个反模式：Vibe Coding 滥用。AI 生成的代码一定要审查。不审查 = 技术债加速器。"

"第四个反模式：工具崇拜。不要一上来就搞 MCP Server、搞 Agent 编排。先让每个人用上 Copilot 再说。"

"第五个反模式：单打独斗。Prompt 经验要共享。谁发现一个好 Prompt，写进共享文档。"
