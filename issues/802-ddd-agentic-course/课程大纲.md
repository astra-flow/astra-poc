## 一、DDD 基础：战略设计与战术设计（40 min）

### 1.1 DDD 是什么（10 min）

- 定义：以领域模型为核心的软件设计方法论（Eric Evans，2003）
- 两大组成部分：
  - 战略设计：限界上下文、上下文映射
  - 战术设计：实体、值对象、聚合、领域服务、Repository
- 适用场景：业务复杂、需长期演进的核心系统

### 1.2 单纯 DDD 的局限（15 min）

| 局限 | 表现 |
|------|------|
| 缺乏"如何开始"的方法 | 知道限界上下文是什么，不知如何发现它 |
| 缺乏客户视角 | 偏开发者-领域专家对话，忽略最终用户 |
| 与现代架构脱节 | 成书于 2003 年，早于微服务与事件驱动 |

### 1.3 Modern DDD：融合方法补位（15 min）

- 业界通称：Modern DDD / Collaborative Modelling
- 四方法补位 DDD 缺口：

| DDD 缺口 | 补位方法 | 作用 |
|---------|---------|------|
| 理解客户视角流程 | 客户旅程图 | 从客户视角描绘触点与痛点 |
| 对齐客户体验与后台 | 服务蓝图 | 5 层泳道揭示后台流程 |
| 快速发现事件与边界 | 事件风暴 | 以事件为锚点协作建模 |
| 从事件推导命令聚合 | 命令风暴 | 从"发生了什么"推导"谁让什么发生" |

## 二、Modern DDD：从业务到模型的完整路径（50 min）

### 2.1 端到端流程（10 min）

```
客户旅程 → 服务蓝图 → 事件风暴(Big Picture)
    → 命令风暴 → 事件风暴(Software Design)
    → DDD 战术设计 → 可落地架构
```

### 2.2 客户旅程图（10 min）

- 输入：客户访谈、客服记录
- 输出：触点序列、情绪曲线、痛点
- 反模式：直接拿功能清单当需求

### 2.3 服务蓝图（10 min）

- 5 层泳道：物理证据 / 客户行为 / 前台 / 后台 / 支持流程
- 三条线：互动线 / 可见线 / 内部互动线
- 关键洞察：后台与支持流程层暴露候选限界上下文

### 2.4 事件风暴（15 min）

- 三个层级：Big Picture / Process Modeling / Software Design
- 核心产物：领域事件时间线、关键事件、候选限界上下文
- 便利贴颜色约定：

| 颜色 | 含义 |
|------|------|
| 橙色 | 领域事件 |
| 黄色 | 角色/用户 |
| 蓝色 | 命令 |
| 紫色 | 策略 |
| 粉色 | 系统 |
| 绿色 | 读模型 |

### 2.5 命令风暴与 Software Design（5 min）

- 核心语法：`Event → Policy → Command → System → Event`
- 聚合边界 = 微服务候选
- 原则：聚合是一致性边界，不是数据库表

## 三、智能体工程：AI 协作的工程化（45 min）

### 3.1 Vibe Coding 与风险（10 min）

- 定义：自然语言意图驱动、AI 生成代码、对话迭代（Karpathy，2025）
- 适用：原型、MVP、简单 CRUD
- 已知风险：
  - AI 代码重大问题多 1.7 倍（CodeRabbit）
  - 安全漏洞多 2.74 倍（CodeRabbit）
  - 成熟代码库中 AI 拖慢 19%（METR）
- 关键分界线：不审查 = Vibe Coding；审查理解 = LLM 辅助编程

### 3.2 智能体工程：从"凭感觉"到"可复利"（15 min）

- 定义：将非确定性 LLM 协作演化为可靠、可复利的工程体系

| 维度 | Vibe Coding | 智能体工程 |
|------|------------|-----------|
| 产出 | 单次对话代码 | 可复用知识资产 |
| Prompt | 凭感觉 | 结构化、有版本 |
| 改进 | 出问题再改 | 持续改进引擎 |
| 能力 | 能做 Demo | 能持续进化 |

- 四层结构：业务层 / Agent 团队层 / 工具平台层 / 治理层
- 核心洞察：问题在业务层暴露，根因在上层

### 3.3 工具链起步（10 min）

- 工具选择：GitHub Copilot / 通义灵码 / Cursor
- 协作：沉淀 Prompt 经验与踩坑记录到共享文档
- 避免：一上来就搞复杂工具链

### 3.4 渐进式实践清单（10 min）

| 阶段 | 动作 | 验收标志 |
|------|------|---------|
| 第一周 | 装好工具，写一个 CRUD | 工具跑通 |
| 第二周 | 辅助写单元测试 | 覆盖率 40% |
| 第一个月 | 共建 Prompt 经验文档 | 10 条以上经验 |
| 第二个月 | 引入事件风暴工作坊 | 产出事件时间线 |
| 第三个月 | DDD 战术设计重构核心模块 | 至少一个聚合落地 |

## 四、两线合一：快速原型法驱动交付（30 min）

### 4.1 快速原型法（10 min）

- 核心：DDD 提供"做什么"，智能体工程提供"怎么做"
- 迭代循环：
  1. 事件风暴工作坊 → 事件时间线
  2. 识别限界上下文与聚合 → 服务边界
  3. AI 工具生成原型 → 可运行 MVP
  4. 客户验证 → 反馈 → 调整模型
  5. 沉淀经验到团队知识库

### 4.2 反模式警示（10 min）

| 反模式 | 表现 | 后果 |
|--------|------|------|
| 功能思维迁移 | 照搬旧系统功能模块设计 | 继承旧系统设计缺陷 |
| 过度建模 | 一上来画全量模型 | 分析瘫痪 |
| Vibe Coding 滥用 | 不审查 AI 代码 | 技术债累积 |
| 工具崇拜 | 一上来搞复杂工具链 | 投入产出比低 |
| 单打独斗 | Prompt 经验不共享 | 团队能力不均 |

### 4.3 落地节奏（10 min）

- 先做核心流程，再逐步细化
- 按业务优先级逐个突破，不一次性设计全部服务
- 每个迭代用事件风暴回顾，模型持续演进
